## Por qué cambia el diseño

`worker/src/pipeline.js` (checkout de `legadoweb`, en producción) ya
modela:

- **Cliente** = IN Client (`resolveClient()`: busca por email, crea si no
  existe). Campos: `name`, `vat_number` (cédula), `phone`, `postal_code`,
  `private_notes`, `contacts[].email`.
- **Plan** = IN Product, discriminado por `custom_value1` ("legadoweb" /
  "urgencias") + `custom_value2` (frecuencia) + `custom_value3` (slug de
  familia) + `notes` (beneficios) + `price`.
- Ya existe precedente exacto del patrón "entidad local referencia IN vía
  custom_value": `admin/admin.js` genera un código de aliado que el staff
  copia a mano al `custom_value4` de cada producto en IN.

Duplicar clientes y planes en tablas `prev_*` nuevas (como proponía el
paquete original, portado 1:1 de Funerzul) crearía dos fuentes de verdad
que divergen. Se optó por: **Invoice Ninja es la fuente de verdad de
clientes, planes, facturación y pagos**; Supabase solo modela lo que
Previsión necesita y que no tiene equivalente en IN (vendedores,
comisiones, beneficiarios estructurados, estatus de contrato, cobranza).

Diseño iterado explícitamente para encontrar huecos antes de escribir
código — ver "Reglas no obvias" abajo, cada una nace de un problema
concreto detectado en esa iteración, no de un capricho de diseño.

## Modelo de datos

### En Invoice Ninja (no se crea nada nuevo en Supabase para esto)

| Concepto Previsión | Objeto IN | Notas |
|---|---|---|
| Cliente | `Client` | Búsqueda por email vía `searchClientByEmail`; cédula en `vat_number`. |
| Plan | `Product` | `custom_value1="prevision"` (namespace nuevo, no pisa `"legadoweb"`/`"urgencias"`). `custom_value2`=frecuencia, `custom_value3`=slug, `notes`=beneficios, `price`=USD. |
| Contrato (parte facturable) | `RecurringInvoice` | Ver asimetría USD/Bs abajo — no todo contrato usa el cron nativo de IN. |
| Cuota (instancia) | `Invoice` | Generada por ciclo, un `Invoice` = una cuota real. |
| Pago | `Payment` | `POST /payments`, soporta aplicar un pago a varias invoices (cascada). |

### Tablas nuevas en Supabase (`supabase/migrations/0001_prevision_fase0.sql`)

Todas con PK `bigint generated always as identity` (consistente con
`locations_venezuela`/`funeral_partners`, que ya usan enteros — ver
`admin/admin.js:313`, `location_id: parseInt(location_id, 10)`).

```sql
-- Sin dependencias
prev_vendedores       (id, nombre, cedula, cargo, supervisor_id → self,
                        pct_comision, retirado, created_at)
prev_parentescos      (id, nombre, edad_min, edad_max)
prev_tasas            (id, fecha, tasa_bs_usd, created_at)

-- Índice delgado hacia IN products (solo lo que IN no modela limpio)
prev_planes_meta      (plan_key text primary key,  -- = custom_value3 del producto en IN
                        activo boolean not null default true,
                        created_at)

-- FK a vendedores
-- NO hay tabla prev_clientes_link (ver regla 1 — cédula NO es única en IN,
-- confirmado en datos reales de producción). La resolución de cliente es
-- explícita por contrato, no un índice cacheado.
prev_contratos        (id, request_id uuid unique,        -- idempotencia (ver riesgos)
                        in_client_id text not null,        -- IN client.id ya resuelto/confirmado por el staff, sin FK real
                        cedula text not null,               -- denormalizado: permite "todos los contratos de esta cédula" sin ir a IN
                        tipo_persona text check (tipo_persona in
                          ('natural','juridica')) default 'natural',
                        in_product_key text not null,      -- custom_value3 del plan en IN
                        in_recurring_invoice_id text,       -- null hasta "activar"
                        vendedor_id → prev_vendedores,
                        estatus text check (estatus in
                          ('borrador','activo','suspendido','anulado',
                           'renuncia','finalizado')) default 'borrador',
                        fecha_ingreso date, fecha_corte date,
                        moneda text check (moneda in ('usd','bs')),
                        monto_ref_usd numeric(19,2),        -- snapshot congelado, ver regla 2
                        tasa_cambio numeric(19,4),           -- tasa vigente al crear (solo Bs)
                        frecuencia text, forma_pago text,
                        created_at, updated_at)

-- FK a contratos, parentescos
prev_beneficiarios    (id, contrato_id → prev_contratos (restrict),
                        parentesco_id → prev_parentescos,
                        nombre, cedula, fecha_nacimiento,
                        estatus text check (estatus in
                          ('activo','suspendido','excluido','fallecido')),
                        created_at)

-- FK a contratos — espejo de control, NO fuente de verdad
prev_cuotas           (id, contrato_id → prev_contratos (restrict),
                        in_invoice_id text,                 -- null = aún no generada en IN
                        tipo text check (tipo in
                          ('inicial','programada','especial','mora','final')),
                        monto numeric(19,2), fecha_vencimiento date,
                        estado text check (estado in
                          ('pendiente','parcial','cobrada','anulada'))
                          default 'pendiente',
                        synced_at timestamptz,               -- última vez que se confirmó contra IN
                        created_at)

-- FK a cuotas y contratos
prev_pagos            (id, contrato_id → prev_contratos (restrict),
                        cuota_id → prev_cuotas (restrict),
                        in_payment_id text not null,
                        monto_usd numeric(19,2), monto_bs numeric(19,2),
                        tasa_cambio numeric(19,4), forma_pago text,
                        fecha date, created_at)
```

No hay `DELETE` duro para `prev_contratos` en Fase 0 — solo transiciones
de `estatus`, igual que Funerzul soft-deletea. `prev_beneficiarios`,
`prev_cuotas`, `prev_pagos` usan `ON DELETE RESTRICT` hacia contratos:
nunca se borra un contrato con historia asociada.

## Reglas no obvias (cada una nace de un problema encontrado al iterar)

1. **La cédula NO es una clave única en IN — confirmado en producción, no
   es una suposición.** Buscando `V-6748677` en el listado de Clients de
   IN aparecen 3 registros distintos de la misma persona (mismo nombre,
   emails diferentes: `estebanvasquez@hot...`, `estebanjvasquez@gm...`,
   `artem@iirport.com`) — consecuencia directa de que `resolveClient()`
   en `pipeline.js` deduplica por **email**, no por cédula (es el mismo
   síntoma que el README ya documenta como limitación conocida — "Sin
   idempotencia en checkout" — con evidencia real de que ya ocurrió).
   Esto tumba la idea original de un índice `cedula → in_client_id` 1:1
   cacheado (`prev_clientes_link`, eliminado del modelo de datos):
   cualquier índice así sería ambiguo o simplemente falso para clientes
   con duplicados.

   **Diseño en su lugar:** la resolución de cliente es un paso explícito
   del staff en el momento de crear el contrato, nunca un lookup
   automático silencioso:
   - `GET /admin/prevision/clientes?cedula=...` devuelve **un array**
     (0, 1 o N candidatos), con `id`, `name`, `contact_email`, `balance`
     de cada uno — los mismos campos que ya se ven en el listado de IN.
   - 0 resultados → ofrecer "crear cliente nuevo en IN".
   - 1 resultado → usarlo directo.
   - N resultados (el caso real, confirmado) → la UI obliga a elegir uno
     antes de continuar; no hay default automático.
   - El `in_client_id` elegido se graba directo en `prev_contratos` (no
     en una tabla intermedia) junto a `cedula` denormalizada — eso ya es
     suficiente para responder "todos los contratos de esta cédula" sin
     depender de que IN tenga una cédula única, y sin fingir que un
     problema de datos preexistente en IN ya está resuelto.
   - Limpiar los clientes duplicados que ya existen en IN (como los 3 de
     `V-6748677`) queda **fuera de alcance de Fase 0** — es un problema
     de higiene de datos preexistente al módulo de Previsión, no algo
     que esta fase deba resolver.

2. **Nunca releer el precio "actual" del plan al generar una cuota.**
   `prevision/contratos.js` siempre usa el `monto_ref_usd` congelado en
   el contrato al crearlo, nunca el `price` vigente del producto en IN.
   Si se releyera el precio actual, un ajuste de tarifa re-tarificaría
   contratos vigentes por accidente — viola la regla explícita de
   Funerzul ("ajustes nunca retroactivos").

3. **Asimetría USD vs. Bs en la generación de ciclos.**
   - Contratos en **USD**: usan el cron nativo de `RecurringInvoice` de
     IN sin cambios — `createRecurringInvoice` + `bulkRecurring("send_now")`,
     igual que hace `pipeline.js` hoy.
   - Contratos en **Bs**: el cron de IN generaría invoices con el costo
     Bs congelado desde la creación, para siempre — viola la regla de
     "actualización manual de tasa" del módulo original. En su lugar, el
     Worker genera cada ciclo explícitamente (acción propia, disparada
     por el Cron Trigger de Fase 0.1 o manualmente), recalculando
     `monto_ref_usd × tasa del día` (`prev_tasas`) en cada generación.
     El `RecurringInvoice` en IN para estos casos existe solo como
     contenedor/registro de suscripción, con `auto_bill:"off"` y sin
     depender de `send_now` automático.

4. **`prev_cuotas` es el plan de pagos proyectado, no un espejo pasivo.**
   Al activar un contrato se generan TODAS las cuotas futuras localmente
   (monto + fecha de vencimiento según frecuencia/plazo), con
   `in_invoice_id = null`. El cron de IN (o el generador Bs del punto 3)
   va materializando invoices reales ciclo a ciclo; un paso de
   sincronización enlaza cada invoice nueva de IN con la cuota **pendiente
   más antigua sin enlazar** que matchee monto — mismo principio que la
   cascada de pagos (aplicar a lo más antiguo primero), reutilizado aquí
   para no inventar una regla nueva.

5. **Sync-then-evaluate, nunca evaluate-from-cache.** Cualquier regla que
   dependa de `prev_cuotas.estado` (auto-lapsado en Fase 0.1, validación
   de solvencia en siniestros en Fase 0.2) debe forzar un refresco desde
   IN de las cuotas relevantes antes de evaluar — nunca confiar en el
   último valor sincronizado sin más. Evita suspender/rechazar sobre un
   estado stale del espejo.

6. **Cascada de pagos vía IN, adelantos vía Credit nativo — confirmado
   viable en el dashboard.** Un pago se reparte localmente (oldest-first)
   entre las cuotas con `in_invoice_id` ya enlazado, y se envía a IN como
   un único `Payment` aplicado a múltiples invoices (`POST /payments`
   soporta esto). Si el monto excede las cuotas ya generadas en IN
   (adelanto a un ciclo futuro que IN todavía no materializó): **sí se
   usa el objeto `Credit` nativo de IN** — confirmado en el dashboard que
   se puede crear un Credit para un cliente sin asociarlo a ninguna
   invoice (solo cliente + productos/monto). El remanente del pago se
   registra como un `Credit` del cliente en IN; el paso de sincronización
   (punto 4), al enlazar la siguiente invoice generada con su cuota, es
   responsable de aplicar el Credit disponible sobre esa invoice. *Sin
   confirmar todavía:* si IN aplica el Credit automáticamente a la
   siguiente factura del cliente o si requiere una llamada explícita
   (`POST /credits/{id}/apply` o similar) — no se verificó si hay un
   toggle "Auto apply" al crearlo. Tratar como manual (llamada explícita
   del Worker) hasta confirmar lo contrario — es el supuesto más seguro:
   si resulta que IN sí lo aplica solo, la llamada explícita del Worker
   sería en el peor caso redundante, no incorrecta. Confirmar antes de
   codificar `prevision/pagos.js` en detalle.

7. **`custom_value4` de productos "prevision" es independiente del de
   "legadoweb".** El toggle activo/inactivo de un plan **no** se guarda
   ahí (evita que la UI de IN muestre "activo/inactivo" bajo una
   etiqueta de campo pensada para otra cosa, como pasa con el campo
   "Aliados" en productos legadoweb) — vive en `prev_planes_meta.activo`.

8. **Lectura defensiva en el límite Supabase↔IN.** `in_client_id` /
   `in_recurring_invoice_id` / `in_invoice_id` son texto libre, sin FK de
   Postgres posible hacia un sistema externo. Cualquier vista que
   necesite datos del cliente los pide fresco a IN (`GET /clients/{id}`)
   en el momento, nunca cacheados en Supabase; si IN devuelve 404, la UI
   muestra "cliente no encontrado en IN" en vez de romper — mismo
   espíritu que el cliente no-op de `supabase.js` cuando falta config.

9. **Idempotencia de creación de contrato.** El frontend genera un
   `request_id` (uuid) al abrir el formulario; `POST
   /admin/prevision/contratos` hace upsert por `request_id` (índice
   único). Un doble click reenvía el mismo `request_id` → no crea un
   contrato duplicado. La creación es dos pasos: (a) insertar el
   `prev_contratos` en `estatus='borrador'` con
   `in_recurring_invoice_id=null`; (b) acción explícita "Activar" que
   llama a IN y solo entonces pasa a `estatus='activo'`. Si (b) falla,
   el borrador queda visible con un botón "Reintentar activación" — no
   se pierde ni se duplica.

## Rutas del Worker (`/admin/prevision/*`)

Heredan `requireAdmin()` automáticamente porque `handleAdmin()` ya hace
ese chequeo antes de dispatchear cualquier ruta — confirmado leyendo
`worker/src/admin.js`, no requiere cambio adicional.

```
GET  /admin/prevision/clientes?cedula=...        → busca en IN, devuelve array (0/1/N candidatos, ver regla 1)
POST /admin/prevision/clientes                   → crea cliente nuevo en IN (solo cuando el GET dio 0 resultados)

GET  /admin/prevision/planes                     → productos IN custom_value1=prevision + join prev_planes_meta
POST /admin/prevision/planes                     → crea producto en IN (custom_value1=prevision) + prev_planes_meta
PATCH /admin/prevision/planes/:key/toggle         → solo prev_planes_meta.activo

GET  /admin/prevision/contratos                  → list, con datos de cliente resueltos en vivo desde IN
POST /admin/prevision/contratos                  → crea borrador (idempotente por request_id)
POST /admin/prevision/contratos/:id/activar       → llama a IN, completa in_recurring_invoice_id
POST /admin/prevision/contratos/:id/estatus       → transición de estatus (nunca DELETE)

POST /admin/prevision/contratos/:id/beneficiarios → CRUD beneficiarios (solo Supabase)

GET  /admin/prevision/contratos/:id/cuotas        → prev_cuotas del contrato
POST /admin/prevision/contratos/:id/cuotas/sync   → fuerza sync contra IN (regla 5)

GET  /admin/prevision/contratos/:id/pagos         → prev_pagos del contrato
POST /admin/prevision/contratos/:id/pagos         → cascada + POST /payments en IN (regla 6)

GET  /admin/prevision/vendedores                  → CRUD prev_vendedores
```

Estilo de respuesta: `{ data: ... }` / `{ error: "..." }`, igual que el
resto de `admin.js` (no el `{ ok: true|false }` de Funerzul).

## Riesgos específicos de esta fase

| Riesgo | Mitigación |
|---|---|
| **Clientes duplicados en IN — confirmado en producción, no hipotético** (3 registros para la misma cédula `V-6748677`, mismo síntoma en toda la base de clientes probablemente) | Regla 1 — resolución explícita con desambiguación manual, cédula denormalizada en `prev_contratos`. Limpiar los duplicados existentes queda fuera de alcance de Fase 0, pero conviene que el usuario lo sepa: es un problema de datos ya presente, no exclusivo de Previsión. |
| Staff elige el `in_client_id` equivocado entre varios candidatos con el mismo nombre/cédula | La lista de candidatos muestra email + saldo + última sesión (igual que la tabla de IN) para poder distinguir; sin esos datos, la desambiguación es a ciegas. Si dos candidatos son indistinguibles incluso con esos datos, no hay mitigación en Fase 0 — anotar como riesgo residual. |
| Contrato Bs con tasa congelada si se usara el cron nativo de IN sin querer | Regla 3 — generación explícita del Worker para Bs, nunca `send_now` automático de IN en ese caso. |
| Cuota "fantasma" si el sync (regla 4) matchea mal una invoice de IN contra la cuota equivocada | Match por monto + cuota pendiente más antigua sin enlazar; si hay ambigüedad (mismo monto, misma fecha), el sync debe marcar la cuota como `en_revisión` en vez de adivinar — agregar antes de codificar el sync. |
| Adelanto de pago sin invoice generada en IN todavía | Regla 6 — se registra como `Credit` en IN; confirmar antes de codificar si requiere aplicación explícita del Worker o IN lo aplica solo. |
| `prev_cuotas`/`prev_beneficiarios` huérfanos si se borra un contrato | `ON DELETE RESTRICT`, sin endpoint de `DELETE` duro para contratos. |
| Blast radius de `IN_TOKEN` (token de compañía completo, no scoped) | Preexistente, no introducido por esta fase. |

## Limitación de esta spec

No fue posible consultar la API REST de Invoice Ninja en vivo desde
ningún entorno de desarrollo — ni este agente ni la máquina del usuario
lograron pasar el *managed challenge* de Cloudflare contra `/api/v1/*`
(403 incluso desde un navegador ya autenticado en el dashboard, lo que
sugiere una regla de firewall que restringe esa ruta por IP de origen,
no un problema de credenciales). Dos puntos se confirmaron igual, por
otras vías:

- **Cédula no es única en IN** — confirmado directamente en el dashboard
  (búsqueda por `vat_number` en el listado de Clients, 3 resultados para
  la misma persona). No se pudo confirmar si existe un filtro de API
  estricto (`?vat_number=`) distinto de la búsqueda difusa que usa la UI
  — para Fase 0 no importa: el diseño (regla 1) ya asume ambigüedad y no
  depende de que exista un filtro exacto.
- **Credits de IN sirven para adelantos** — confirmado en el dashboard
  (se puede crear sin asociar invoice). Pendiente confirmar solo el
  detalle de auto-aplicación (regla 6) — no bloqueante, se puede
  implementar asumiendo aplicación manual y ajustar después si se
  descubre que IN ya lo hace solo.

Nada de Fase 0 queda bloqueado por la falta de acceso a la API en vivo:
el resto del diseño se apoya en la lectura completa de
`worker/src/pipeline.js` y `worker/src/invoiceninja.js` (código real en
producción, más confiable que un snapshot). El único paso pendiente
antes de codificar `prevision/pagos.js` es confirmar el detalle de
auto-apply de Credits mencionado arriba — se puede hacer creando un
Credit de prueba real y observando qué pasa en la siguiente factura del
cliente, no requiere acceso a la API.
